你可以带着一个具体问题来，比如“并发发生变化时，基准测试报告的峰值是否准确？”，也可以让 RepoScout 自行探索。每个仓库由一个子 agent 负责。它先检查上游已有的讨论和改动，再设计能验证想法的最小实验。等到有了代码、基线和实测结果，你再决定是否向上游发布。

## 快速开始

**1. 安装 skill。** 在 Codex 中发送：

```text
$skill-installer 请从 https://github.com/HaoyangPing0324/RepoScout 安装 skills/reposcout 目录下的用户级 skill。
```

**2. 在工作区开启新对话。** 下面是一条可以直接改的示例。路径换成你希望存放目标仓库的位置。

```text
$reposcout 探索 vllm-project/vllm，工作目录用 ~/work/vllm，单个 PR 模式。
我想检查 benchmark 对峰值并发的统计。先用一个可以手算的请求序列验证；
如果已经有人修复，请继续寻找同一模块里值得验证的问题。
```

也可以只给仓库名。RepoScout 会询问你的工作目录，以及是否已有想验证的点子。默认所有指定仓库持续探索，也可以明确指定某个仓库只做单个 PR。实验需要服务器、数据或 GPU 时，它会告诉你需要什么、用来验证什么；你可以当场提供资源，或让这项实验排队。

| 模式 | 第一份 PR 准备好之后 |
| --- | --- |
| 单个 PR | 停止寻找新候选，等待你审核，按反馈修改或发布这一项。 |
| 连续探索 | 当前版本送审后，同一仓库立即开始下一项，在独立 worktree 中继续探索。各仓库可分别选择模式。 |

连续探索随当前活跃会话运行。一个实验等 GPU、CI 或你审核时，负责人保存版本、命令和恢复条件，接着做同仓可执行的方向。工作台记录候选实验状态，派工表另外显示仓库当前在做什么、谁已开工。父 agent 对照运行列表补上意外空出的槽位；会话中断后，恢复时先核对仍在运行的作业。你明确叫停的仓库退出轮转。[连续探索的运行调度](skills/reposcout/SKILL.md#连续探索的运行调度)

## 怎样选择更可能合并的贡献

同时指定多个仓库时，主 agent 先给你一份《仓库 PR 审核与合并对比》。第一张表比较同一周新开的外部 PR，回答“两周内合并了多少、通常要等多久才有人正式评审”；第二张表解释本轮先做哪个候选、谁排队、什么时候重排。报告交付后才分配子 agent 或设备，并把实际分配写回同一文件。[查看报告模板](skills/reposcout/assets/仓库PR审核与合并对比.md) · [复算方法](skills/reposcout/references/repository-comparison.md) · [六仓库报告示例](skills/reposcout/references/repository-comparison-example.md)

每个仓库有一名负责人，同时查两件事：领域里近期有哪些方法值得在这个仓库验证，维护者最近又接受或搁置了哪些同类改动。比如一篇论文提出新的调度策略，负责人会核对它是否适用于仓库当前实现，再看同模块的外部 PR 是否被要求补充特定负载下的延迟数据。两边的证据一起决定先做哪个实验。

遇到一行看似写错的判断，RepoScout 会先追溯引入它的提交、上游讨论和回归测试。例如，边界条件用的是 `>` 还是 `>=`，要结合调用方能否传入该值、接口对相等情形的约定来判断。确认现版本能复现偏差后，再用相同用例检验修正，同时复测原判断保护的场景。若行为符合设计，就关闭误报。[疑似缺陷的验证方法](skills/reposcout/references/exploration.md#核实疑似缺陷)

跨仓库分配会随结果变化。假设 A 最近只有一个相关 PR，B 刚合并多项同类外部贡献，而且还有几个互不重复、能够验证的方向，父 agent 可以把更多槽位给 B。连续模式下，B 的负责人可以创建方向子 agent，分别在独立 worktree 开工。B 可能准备好七项贡献时 A 才有一项；这个比例由证据和资源决定。上游合并、关闭或提出新要求后，下一轮会重新排序。[候选比较与扩编方法](skills/reposcout/references/exploration.md)

## 多个仓库如何共享资源

假设三个仓库的实验分别需要 8、4、8 张 GPU，你提供一台有 16 张空闲卡的服务器。父 agent 可以按下表协调，子 agent 知道自己可使用的物理卡号和工作目录。

| 时点 | 仓库 A · 8 卡 | 仓库 B · 4 卡 | 仓库 C · 8 卡 |
| --- | --- | --- | --- |
| 首轮分配 | GPU 0–7 | 等待，可先做 CPU 测试 | GPU 8–15 |
| A 的作业退出后 | 释放 GPU 0–7 | 获得 GPU 0–3 | 继续使用 GPU 8–15 |

如果获准使用的卡上已有他人的作业，RepoScout 会把这些卡记为占用，改用空闲卡或排队。即使进程属于同一登录账号，也只有确认属于本轮实验的作业才可管理。每个资源请求都会单独转达。分配时核对物理主机、可用设备和独占目录，释放时核对实际作业状态。一个仓库的 PR 等待审核期间，其他仓库可以继续实验。[完整调度流程](skills/reposcout/SKILL.md)

## 在对话中查看进度和答辩

主 agent 在对话启动目录维护 `.reposcout/TASKS.md`，你可以直接说“列出三个表”。**待审核**列出可答辩的版本、材料和待决动作，**处理中**列出负责人、实验进度或返工事项，**处理完成**保留处理结论和 PR、Issue 或本地证据链接。[查看三表模板](skills/reposcout/assets/TASKS.md)

同一仓库有 **6 项或更多尚未发布的 PR 候选等你审核**时，主 agent 会自动检查哪些小改动适合归成一个 PR，各仓库同时继续探索。例如两个入口都漏掉了同一项兼容处理，可以一起修复，用同一组用例验证。整合通过后，你只需审核一份新版本，旧编号仍可追溯。即使只有一两行修改，也会先寻找相关候选；确有独立价值的小修复可以保留。[归并规则](skills/reposcout/references/exploration.md#待审候选归并)

例如，连续模式下，`RS-003` 的实验做完后进入待审核，同仓库的 `RS-004` 立即进入处理中。你可以说“先答辩 RS-003，解释两组实验的输入是否相同”。如果需要补测，`RS-003` 会沿用编号回到处理中；补齐证据后再送审。你也可以只批准某个版本发布 PR，单独决定是否开 Issue。

要看已经发起的贡献，可以说“列出这个工作区发过的 PR 和对应 Issue”，或打开对话启动目录下的 `PR_INDEX.md`。这张表跨仓库、跨会话累计，每个 PR 一行。它和三张工作表都显示改动量，例如 `-8 / +24` 表示删 8 行、增 24 行。已发布的 PR 采用 GitHub 的统计，归并候选按整合后的完整 diff 重新计算。先开 PR、后来再关联 Issue 时，主 agent 会把链接补到原行；已经合并或关闭的 PR 也保留。[查看发布总表模板](skills/reposcout/assets/PR_INDEX.md)

## 收到待审通知后看什么

每个通过实验验证的候选都会保留工作分支或补丁，并附上四份材料。建议先读 `REVIEW.md`，看实验能否支持改动，再审对外发布的正文。

| 文件 | 回答的问题 |
| --- | --- |
| `REVIEW.md` | 为什么改？基线和改动版本分别得到什么结果？怎样复核，结论适用于哪些条件？ |
| `REQUIREMENTS.md` | 上游要求哪些测试、模板或 AI 使用披露？哪些已有证据，哪些还要等待 CI？ |
| `PR.md` | 维护者将看到什么标题和说明？这份改动如何解决问题？ |
| `ISSUE.md` | 如果值得单独开 Issue，其他人如何复现问题或判断建议是否实现？ |

主 agent 会在对话里向你答辩。它先解释为什么值得改、哪组对照支持结论、结论在哪些条件下可能失效，再逐条回答你的追问。如果你质疑两次实验的负载不同，它会核对记录，必要时安排同条件复测，带着新结果回来。你可以要求修改、搁置，或明确批准某个仓库、候选版本和发布动作。PR 和 Issue 分别审批。开 PR 前，主 agent 会列出发布账号、全部新增提交的作者姓名和邮箱，以及共同作者（无则注明），请你连同发布动作一起确认。新增提交使用你确认的人类作者身份，遵循上游披露要求；遇到无法满足的署名要求时，RepoScout 保留本地结果并说明冲突。[审核与发布说明](skills/reposcout/references/review.md)

## 邮件通知

首次使用时，RepoScout 默认在**开启对话的目录**创建 `smtp.env` 并给出文件链接。按文件中的中文说明填写 SMTP 发信服务器、端口、加密方式、登录名、授权码和自己的邮箱地址。本轮所有仓库共用这份本地配置。

某个候选准备好后，你会收到一封自己发给自己的邮件，内含仓库名、候选版本和本地审核目录。邮箱尚未配置或发送失败时，当前对话也会给出审核材料的位置。通知脚本使用 Python 3 标准库。
