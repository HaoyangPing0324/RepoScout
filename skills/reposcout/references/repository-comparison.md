# 首次派工前怎样比较仓库

父 agent 亲自做只读调研。把用户给的仓库规范成 owner/repo，去重；无权访问的仓库也占一行，注明缺失原因。将[报告模板](../assets/仓库PR审核与合并对比.md)复制到启动目录的 `.reposcout/仓库PR审核与合并对比.md`，展开为每表每仓一行。报告所用的原始数据或最小字段快照放在同一私有目录下，保留历史快照或版本。多仓库清单、窗口和筛选条件均来自本轮，勿沿用示例中的名称或统计值。

## 统一窗口与分母

- 先固定一个统计时点 T 和报告时区（默认 UTC，可用用户指定的 IANA 时区），所有仓库共用。自然周按当地周一 00:00 开始，取满足“结束时刻 + 336 小时 ≤ T”的最近一周，左闭右开。例如 T 为 2026-11-25 12:00 UTC，默认创建窗口是 11-02 至 11-08，11-09 00:00 为右端。时间差按 UTC 时间戳计算。
- 抓取窗口内创建的全部 PR，含草稿、仍开放及关闭未合并。外部作者取 GitHub 的 NONE、CONTRIBUTOR、FIRST_TIMER、FIRST_TIME_CONTRIBUTOR。OWNER、MEMBER、COLLABORATOR、MANNEQUIN 单列排除。按账号类型 Bot、登录名以 [bot] 结尾、或有来源证实的自动化账号排除机器人。仓库有明确的镜像、批量导入、自动同步标签、账号或来源分支时，据此排除并逐项记录原因。勿按补丁大小或单一模糊标题猜测。每个 PR 只扣除一次。作者身份缺失且无法判定时，给出缺失数量，完整 cohort 指标标“数据缺失”。
- 令 N 为该周全部合格外部 PR，K 为其中 `created_at ≤ merged_at ≤ created_at + 336h` 的数量。展示 K/N（如 36.6%（34/93））。同批直到 T 才合并的也计入**已合并者用时中位数**，包括超过 14 天才合并者。展示其中位耗时和样本数。N=0 写“无合格样本（0/0）”，N>0 且 K=0 写“0.0%（0/N）”，无已合并者时中位数写“无已合并样本”。
- 开放数单独获取全仓所有当前开放 PR 的总数，含成员、机器人和草稿，标注实际查询时刻。近 30 天取报告时区截至统计日零点之前的 30 个完整自然日。对全仓取窗口内合并数 M 和窗口内关闭且未合并数 C，显示 M、C、M/(M+C)；无结案写“无结案样本”。保留同批外部统计和全仓对照各自的分母。

## 取数与复算

可用 GitHub REST、GraphQL 或已授权的 GitHub 工具。将以下查询换入真实仓库及时间，然后在成品里留下可点开的链接。

1. 用 `repo:OWNER/REPO is:pr created:START..END` 枚举创建窗口（转 UTC，在本地严格裁剪右端）；用 `repo:OWNER/REPO is:pr is:open` 查开放总数。结案分别查 `is:pr is:merged merged:START..END` 和 `is:pr is:closed is:unmerged closed:START..END` 并限定仓库。GitHub 的区间搜索含两端，时间戳查询将右端设为结束前一秒；UTC 整天查询用最后一个纳入的日期。记录所有计数查询，包括 0。GitHub 搜索最多返回 1,000 个结果；枚举时按时间切段并分页、按仓库和编号去重、核对总数。若某时间段仍截断，继续细分或改用可完整分页的 PR 列表。超时、限流、访问不足或分页不全时逐项标“数据缺失”，已核实的其他指标可以交付。[GitHub 搜索 API](https://docs.github.com/en/rest/search/search#search-issues-and-pull-requests)
2. 从全部合格 PR 中按确定性规则取 12 个，不足则全取：按 SHA-256 的原始字节升序，输入为 UTF-8 的 `小写owner/repo|创建窗口周一YYYY-MM-DD|PR十进制编号`，同值按编号升序。种子与样本列表写入报告。逐条分页读取 GitHub PR reviews。取截至 T 首个非作者、非机器人的已提交正式 review，包含 APPROVED、CHANGES_REQUESTED、COMMENTED 和提交后被 DISMISSED 的 review。排除 PENDING、自评和普通 Issue/行内评论事件；评审人无需是仓库成员。等待从 PR 创建时刻算起，可以超过 14 天。记录 review 链接及时间。[GitHub Reviews API](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request)
3. 展示“7/12 有首评，中位 11.8 小时”，中位数仅取已收到的首评。只有一个写“1/12 有首评，实际等待 22.6 天”。全部查完且无人评审时写“0/12 有首评，截至 T 仍未见”；部分未能查询时写“7/12 已知有首评，3 项未见，2 项数据缺失”，统计值标为已知样本。未知身份的更早评审要核实，不能跳过后宣称下一条就是首评。

可用随 skill 分发的[统计脚本](../scripts/pr_cohort.py)复算。它只读取快照。每仓 JSON 顶层含 `repo`、带偏移的 `as_of`、`timezone`、`cohort_complete`、`pulls`、`reviews`。每个 PR 需要 `number, created_at, merged_at, author_association, user, excluded_reason`；后两项分别为含 login/type 的用户对象和排除原因（正常填 null）。首次用 `python pr_cohort.py snapshot.json --sample-only` 获得样本编号。填入以 PR 编号字符串为键的 reviews，每条含 state、submitted_at 和 user，脚本复用 GitHub 的账户类型及 [bot] 规则；已核实的额外自动化账号在输入中标记 type=Bot 并保留原始证据。确认读取完整的空列表写 []，缺失或抓取不全写 null。再用 `python pr_cohort.py snapshot.json` 取得人数、时长和逐条观测，配合查询所得全仓计数填写模板。保留原始链接、排除清单、窗口和快照，便于他人重算。

## 报告怎样驱动派工

在第二张表给每个仓库写一个具体候选、模块证据、顺序和重排条件。在价值、维护者需求、验证成本相近时，优先近期同模块接受过外部贡献、14 天比例较高且人工响应较快的仓库。将用户优先级、维护者邀请、重复实现、上游政策、样本量和实际可用设备逐项落实到相应行。样本量不足时优先看直接证据。历史比例只描述这批 PR。

**先交付，再派工。** 交付时，第二表“实际分配”如实写 0，在优先级和排队原因说明下一步准备给谁多少资源。父 agent 在聊天发出文件链接和简短结论后，按报告立即发起获准的派工，无需等用户回复；只有收到 agent 标识或完成设备分配才回填实际数和设备清单。启动失败、设备被占用或槽位不足也在同一表即时记录。恢复会话、重要 review、PR 合并/关闭、资源释放时先复核顺序。同一天且口径相同的统计可以复用，标明原采集时间；每次实际派工变化仍更新分配表。用户明确停止的仓库从探索和资源等待队列移出，核实在运行作业收尾后释放资源，在报告保留既往结论和停止记录。
