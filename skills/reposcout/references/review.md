# 审核包

在父 agent 的私有运行目录按仓库和候选分目录保存材料，记下基线 SHA、工作分支、worktree 和候选版本。未经发布批准时可以保存工作区改动和补丁；用补丁摘要或已有 commit SHA 标识审核版本。创建补丁时包含计划交付的新文件，并核对审核过的改动与将要提交的内容一致。

| 材料 | 面向谁 | 必含内容 |
| --- | --- | --- |
| PR.md | 上游维护者 | 可直接提交的标题和正文，遵循仓库模板，写明动机、实现、验证和关联 Issue。 |
| ISSUE.md | 上游维护者 | 一份可独立发布的标题和正文。缺陷写复现条件、期望和实际行为；改进建议写使用场景、当前限制和验收方式。 |
| REVIEW.md | 用户 | 为什么做（相关前沿来源、可比 PR 及维护者反馈）、具体改了哪里、采用了什么措施、基线与改动的实测结果、如何复核、局限与待决定事项。 |
| REQUIREMENTS.md | 用户 | 按项列出目标仓库贡献要求、来源链接或文件位置、符合情况和证据。标明尚待 CI、未验证和阻止发布的项目。 |

使用上游要求的语言写 PR 和 Issue，用用户的语言写审核说明。命令、配置和数据应足以重做实验，性能对比保留相同的环境和负载。适用于公开正文的日志先去除凭据和私有环境细节。若本地检查没有跑过，在对应项明确标记。

## 答辩

父 agent 先展示三表工作台中该编号的待审核行，再在主对话里讲清三个问题：上游为什么需要这项改动，哪组基线、测试或对照支持结论，最可能改变结论的条件是什么。指向具体 diff、命令和结果，并说明尚待 CI 的项目。最后邀请用户质询，或直接对指定版本作发布决定。用户已充分了解并明确批准时，可以当轮结束答辩，无需固定问答轮数。

逐一回应用户的异议。例如，用户质疑“加速是否来自不同的输入长度”，父 agent 应当拿出两次运行的负载记录。记录不足就承认该结论尚待验证，安排原负责人用相同输入复测，再带着结果和更新后的结论回来。将问题、证据、待办和用户决定追加到该候选的本地 `REVIEW.md`。实质改动或正文更新后，标识新版本，说明变化，请用户裁决。用户可选继续修改、搁置或明确批准发布 PR、Issue 中的指定项。

## 确认 PR 作者名单

答辩时，主 agent 在本地 `REVIEW.md` 和主对话中列出候选编号与版本、拟开 PR 的 GitHub 账号、本次全部新增提交的作者（姓名和提交邮箱），以及所有 `Co-authored-by` 共同作者；无人共同署名时明确写“无”。若先审补丁，标明“拟用署名”，获准创建提交后再核对实际结果。将“确认名单并发布 PR”列入待审核行，用户可以一次回复同时批准这两件事。

以目标仓库实际 base 和候选 head 的 SHA 确定 PR 范围，核对每一笔提交，包括非末尾提交。可用以下命令查看原始作者身份和 Git 解析的共同作者：

```sh
git log --reverse --format='%h %an <%ae>%n%(trailers:key=Co-authored-by)' "${base_sha}..${head_sha}"
```

推送前将实际结果与已确认名单比对，开 PR 前再核实当前发布账号及远端 base/head 对应已审范围。名单、账号或提交范围发生未获确认的变化时，保留待审核状态，指出具体差异再请用户裁决。曾按补丁获批的改动，创建提交后确认内容及署名均吻合即可继续。遇到他人已有提交，保留原署名并核对分支范围。确认结果只适用于本候选，不影响同仓库继续探索。

## 邮件

从本次对话的启动目录运行初始化命令，默认生成该目录直属的 `smtp.env`。如果已经切换了目录，则向命令传入启动目录下的配置绝对路径；用户指定其他位置时同样传入绝对路径。记录最终路径供后续发送使用。

写入前，若配置位于 Git 工作树内，用 `git ls-files --` 检查目标文件是否已被跟踪。已跟踪时提醒用户改用私有路径；未跟踪时把该文件相对仓库根的精确路径加入本地 `info/exclude`，用 `git check-ignore` 验证。已有配置保留。将配置链接交给用户在本地填写，密码不进入聊天。

```sh
python <skill目录>/scripts/notify.py --init
```

文件内逐项说明服务器、端口、加密方式、登录名、授权码和收发邮箱的填写方法。每个候选进入待审时，父 agent 先在运行记录里登记待通知，向用户自己的地址发送仓库、候选、版本及审核包本地路径。邮件只负责提醒。示例：

```sh
python <skill目录>/scripts/notify.py <本次对话记录的配置绝对路径> --repo owner/repo --candidate RS-001 --revision <版本> --review-dir <审核包目录>
```

脚本退出码 0 表示 SMTP 已接受（初始化模式除外），1 表示配置错误或确定失败，3 表示投递结果不明。SMTP 服务接受后记录该版本已通知。配置缺失或确定失败时，在聊天中即时报告待审项和材料路径，保留待通知记录，修复后补发。若在投递时连接中断而结果不明，先核实是否已收到，再决定是否补发。恢复时跳过已通知的版本。用户在其审核渠道明确批准对应候选后才处理发布，邮件送达本身不代表批准。
