# 如何选择值得投入的方向

仓库负责人在初选候选时并行检索下面两类证据。把检索日期、窗口、来源链接和结论写入本地运行记录。准备占用稀缺设备、扩编或提交审核时，复查候选是否已有实现、相关讨论是否有新结论。

| 需要判断 | 去哪里查 | 带回什么 |
| --- | --- | --- |
| 技术上有什么值得验证？ | 近期原始论文、官方实现与发布说明、相关项目的 benchmark，以及目标仓库路线图 | 具体方法适用的版本和条件、与目标模块的差距、可证伪的假设和最小实验。检索没有发现适用进展时直接记录。 |
| 上游近期愿意接收什么？ | 同模块外部贡献者的已合并、关闭未合并、仍开放 PR，关联 Issue 和维护者的 review | 可比 PR 链接、维护者实际要求的测试或数据、响应情况、尚无人处理的需求，以及拒绝或搁置理由。 |

## 核实疑似缺陷

1. **先写明可检验的分歧。** 指出哪个受支持的版本、入口、配置和输入会触发该行为，用户实际会观察到什么，以及文档、接口约定或维护者说明给出的预期。沿调用链检查输入是否在更早处已被归一化、过滤或拒绝。
2. **检索为什么这样实现。** 从相关测试、注释和调用方入手，用 `git blame` 定位引入判断的提交，读完整 diff，再按函数名、条件或提交号查原始 PR、review、关联 Issue 及后续修订。重点找这个判断曾修复的回归、兼容的旧格式或有意接受的取舍。记录能定位到行、测试或讨论的出处。历史没有说明动机时，明确写“原设计动机未知”，将推测与已知事实分开。
3. **用同一组用例比较两种实现。** 先在目标分支的未修改基线上从正常入口复现，再用相同输入、配置和断言测试拟议改动。除了触发异常的例子，也要覆盖原判断保护的场景。例如怀疑应把 `>` 改成 `>=` 时，先查边界值的约定，再验证边界两侧和相等时通过实际入口得到的结果。
4. **根据证据决定去留。** 受支持场景确有偏差、修正能消除偏差且保留原有保证时，才建议按缺陷修复推进。若原行为符合约定，可关闭误报；若希望改变现有约定，则按行为变更讨论收益、兼容代价和迁移方式。证据不足时记录未决问题和下一项验证，保持候选待查。即使原作者未解释动机，也可依据明确约定与可重复的对照结果作判断。

## 待审候选归并

**选题时先看已有工作。** 对一两行的改动，先查同仓库候选是否涉及同一用户问题、根因或接口约定，优先将改动和必要的回归测试放进同一份贡献。即使未达到积压阈值也可以归并。独立且影响明确的小修复可以单独保留，并在审核说明中解释原因。

**按仓库触发。** 统计该仓库“待审核”表中仍需用户裁决是否发布 PR 的候选编号，每个编号计一次。已在 GitHub 发起的 PR（含 Draft）、只等 Issue 决定的行、已结案的原编号均排除。超过 5 项时扫描全组；队列持续超限时，有新候选或新版本就重新比较。将已检查的编号和版本记入现有工作记录，恢复时续办未完成的整合；内容未变的组合免于重复派工。若没有适合组合的项，保留各自结论并继续探索。

**按一个可验收的目标分组。** 例如读入旧格式和恢复检查点走不同入口，却漏用了同一条兼容规则，这两项可以用同一个上游问题和一组回归用例验收。只因都涉及“性能”、修改同一文件或都很短，尚不足以归并。由仓库负责人在独立 worktree 中基于共同目标分支整合，复跑各原候选的验证，再验证它们同时生效的路径和整份 diff。符合上游偏好的审查粒度时才送审，避免用无关修改扩大补丁。

**交接审核版本。** 父 agent 在“处理中”登记整合编号和来源编号，在原待审行标注“整合中”及去向，同一原项同时只派给一个整合任务，保留原工作树、证据和用户意见。整合期间收到对原项的裁决，先核对当前版本与用户意图，再调整分组。整合失败或放弃时，去除原项的整合标记，保留独立待审版本，将整合编号移入“处理完成”并记录原因。验证通过后，一次更新三表：整合编号进入“待审核”，原编号移入“处理完成”并注明“已归入”及目标编号。整合版重备四份审核材料，引用各子项证据，重新答辩并确认署名和发布动作。原版本的同意不自动适用于新范围。用户用旧编号提问时，指向当前审核项。发布后按实际 PR URL 在总表登记一次，列出所有相关 Issue。

## 跨仓库调度

**比较仓库。** 多仓库首次派工严格采用[统一创建周、正式评审抽样及全仓对照](repository-comparison.md)。同模块的 PR 和 review 用于解释候选适配度，保留链接；不要用模块样本替代报告里的全仓计数。

**分配下一份投入。** 父 agent 比较所有获准仓库的候选，优先支持维护者明确需要、近期接收过同类贡献、可用现有资源验证且有独立价值的方向。考虑负责 agent 以往实验能否复核、审核返工量和实际上游结果。一个冷门仓库的明确需求可以排在热门仓库的重复改动之前。给出候选、支持与反对证据、下一步和需要的槽位或设备。每轮连续探索开始时，先只读刷新此前已发布且尚未结案的 PR 状态和 review。遇到新候选、review 反馈、PR 合并或关闭、资源释放时重排队列。记录实际结果（本地待审、上游待审、已合并、关闭未合并），保留仓库和 PR 链接供下轮校准。

**同仓并行。** 在连续模式下，仓库负责人发现多个可独立验收的候选时，可根据以往贡献质量、候选证据或上游近期接受情况向父 agent 申请槽位，说明每个方向的负责人、工作范围、预期验证和资源需求。父 agent 在全局预算内分配槽位后，仓库负责人可自行创建方向子 agent，同时推进。每个子任务有独立分支或 worktree、实验目录和审核包。共享代码改动或同一根因的修复交由一人统筹，避免重复劳动或拆分同一贡献凑数。方向子 agent 通过仓库负责人即时上报需求，物理资源和发布动作仍由父 agent 协调。完成或失去上游需求时回收槽位。运行环境不支持嵌套时，父 agent 可代建并将结果交回负责人；槽位耗尽则排队。单个 PR 模式允许并行调研、测试和复核，最终只交付一个候选。
