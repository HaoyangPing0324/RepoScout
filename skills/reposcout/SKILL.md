# RepoScout

## 开始一轮探索

父 agent 从用户已有信息中提取以下四项，一次询问缺项。允许每个仓库选择不同的模式。

| 仓库 | 起点 | 工作目录 | 模式 |
| --- | --- | --- | --- |
| owner/repo 或 URL | 用户的具体想法，或授权自行探索 | 此仓库的本地工作目录；远端实验目录可稍后申请 | 单个 PR 或连续探索 |

父 agent 在切换工作目录前，记录**用户开启本次对话时的目录**。SMTP 配置默认直接放在该目录下，文件名为 `smtp.env`。用户明确指定路径时使用指定路径。首次调用即可按[邮件初始化说明](references/review.md)创建带中文填写指引的配置，并把实际文件链接给用户。后续通知始终使用这个绝对路径，本轮所有仓库共用一份。

在用户指定的工作区维护运行记录和审核材料，可放入私有目录 `.reposcout/`。如在 Git 工作树中，先确认私有目录没有已跟踪的文件，再加入本地 exclude 并验证。各仓库使用独立 checkout，各候选使用独立分支或 worktree，以便用户审核上一项时下一项仍可推进。保留已有修改。

## 派发和协调

1. 每个仓库创建一个子 agent，由它持续负责该仓库。派发仓库、起点、模式、目录、已获授权的范围和回报方式。超出并发槽位的仓库排队，一旦有位置就派发。父 agent 留在当前会话，处理工作结果、用户消息和资源申请。
2. 子 agent 先读仓库自己的贡献说明、已有 Issue 和 PR，检查候选是否已解决或有人在做，同时检查影响整仓的贡献和署名政策。发现本轮所有 PR 都会遇到的硬性冲突时立即报告，保留已有工作并暂停该仓库的 PR 探索，其他仓库继续。给出对应代码、可检验的假设、最小实验及判定依据。可以探索正确性、性能、测试、可用性和新功能。失败或重复的想法记录证据、关闭候选，继续寻找能完成本轮任务的想法。
3. 子 agent 一发现缺条件就立即向父 agent 发消息，说明仓库/候选、用途、所需资源和可接受的替代方案；能并行的本地工作继续做。父 agent **每收到一项就立即向用户转达**，并说明已有授权能否满足、是否排队；需要补充时使用即时用户提问渠道。不要等待其他仓库汇总。用户已给的材料可直接分发。
4. 资源由父 agent 统一记账，它是本轮分配表的唯一写入者。先记录用户授权的主机、物理卡号或 UUID、目录、额度和期限，再按子任务记录等待、已分配和已释放。对机器别名核实是否指向同一台物理机。分配前核实可用状态，已有占用须尊重；同一物理设备、独占目录或已被整机独占的主机不得重复分配；共享主机上的不同卡可并行使用。给子 agent 明确主机、设备清单、运行目录和用途，让它显式绑定这些卡，核对进程实际可见的设备。涉及其他人的进程时只观察。
5. 例如同一台机器授权 GPU 0–15，A、B、C 分别需要 8、4、8 卡。若拓扑合适且卡空闲，可给 A 分 0–7、C 分 8–15，立即告知 B 排队；A 结束且确认作业退出后，再给 B 分 0–3。子 agent 完成实验、失败或中断均回报作业状态；父 agent 确认资源实际空闲再释放，并唤醒等待者。等待期间允许 B 继续 CPU 工作。恢复会话时先用运行记录核对实际作业，再重新分配。
6. 子 agent 只在获批范围内实验，记录基线/改动版本、配置、命令、结果和局限。实验未达到判据就如实记录，必要时修订假设。每个通过验证的候选按[审核与通知](references/review.md)交付改动和四份材料。父 agent 逐项检查、记录候选版本，立即通知用户可以审核。

## 停止、继续和发布

- **单个 PR**：第一份经验证的 PR 进入待审后，停止寻找新候选，处理该项审核意见。仅在用户明确批准对应版本和动作后提交或发布；按用户的关闭决定或批准的发布结果结束该仓库任务。
- **连续探索**：一份 PR 进入待审即可在独立 worktree 开始下一项，保留待审队列。一次实验失败、通知失败、已有 PR 等待审核或发布成功都不结束探索。收到用户停止指令后停止派新任务，协调运行中的作业收尾并保留结果；真正缺少必要输入时保留阻塞状态。运行依赖活跃会话，中断后从记录恢复。
- 审核意见可以直接交给原子 agent 修订。授权应能定位仓库、候选、版本和动作。PR、Issue 分别发布；批准 PR 不自动批准单独发 Issue。改动或拟发布正文有实质变化时，提交更新后的材料再审。父 agent 执行获批动作，记录远端链接；网络结果不明时先核对远端，避免重复创建。
- 使用用户确认的人类 Git 身份作为新增提交的唯一作者，不加 AI 共同作者或相关 trailer，不改写他人的提交。审核时如实列出上游 AI 政策、披露及签署要求；若上游接受单作者并另要求在 PR 正文披露，则在待审正文中如实披露。若上游强制 AI 共同署名或禁止本次贡献形式，保留本地成果，说明具体冲突，不代用户签署不实声明或发布不符合要求的版本。
