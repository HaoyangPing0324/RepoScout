# RepoScout

以下流程在用户委托探索目标仓库时启动。用户要求完善 RepoScout 项目本身时，按项目维护任务处理，仅修改和验证本次涉及的实现或说明。

## 开始一轮探索

父 agent 从用户已有信息中提取以下四项，一次询问缺项。所有指定仓库默认连续探索；用户明确为某个仓库选择单个 PR 时，按该例外执行。

| 仓库 | 起点 | 工作目录 | 模式 |
| --- | --- | --- | --- |
| owner/repo 或 URL | 用户的具体想法，或授权自行探索 | 此仓库的本地工作目录；远端实验目录可稍后申请 | 单个 PR 或连续探索 |

父 agent 在切换工作目录前，记录**用户开启本次对话时的目录**。SMTP 配置默认直接放在该目录下，文件名为 `smtp.env`。用户明确指定路径时使用指定路径。首次调用即可按[邮件初始化说明](references/review.md)创建带中文填写指引的配置，并把实际文件链接给用户。后续通知始终使用这个绝对路径，本轮所有仓库共用一份。

在用户指定的工作区维护运行记录和审核材料，可放入私有目录 `.reposcout/`。如在 Git 工作树中，先确认私有目录没有已跟踪的文件，再加入本地 exclude 并验证。各仓库使用独立 checkout，各候选使用独立分支或 worktree，以便用户审核上一项时下一项仍可推进。保留已有修改。

## 主对话的三张表

父 agent 在对话启动目录的私有目录维护 `.reposcout/TASKS.md`。首次从[空表模板](assets/TASKS.md)创建，恢复时读回原表并核对工作目录、待审版本和已发布链接。已有运行记录但尚无表格时，先按记录补入已有候选。三张表覆盖本轮所有仓库，由父 agent 串行更新；子 agent 用消息报告事件。为每个候选分配工作台内唯一且稳定的编号（如 `RS-001`），跨表移动、返工和版本更新都沿用原编号。一次写入完成移行，同一编号只出现一次；重复报告按编号和版本核对，旧报告不得覆盖新版本。

- **处理中**：接手探索、等待资源、实验、按意见补测，或执行已批准的发布动作时，登记负责人和下一步。发布结果暂时不明时保留在这里，核对远端后再结案。
- **待审核**：代码和四份材料就绪后锁定版本，移入本表，链接审核包，写明待回答的问题和 PR、Issue 各自的待决动作。问答期间保留此行；需要修改或补测时移回“处理中”，完成后用同一编号和新证据再次送审。
- **处理完成**：获批动作均已执行，或候选明确放弃、实验否定、用户决定结案时移入本表。保留最终版本、结论及远端链接或本地依据。已发布的 PR 单独注明上游待审、已合并或关闭未合并；同一候选若仍有待决定的发布动作，继续列在待审核。

三张表用于对话。用户查进度时直接展示三表，可按指定仓库筛选；答辩、退回或批准时先读取当前行，在聊天中展示编号、仓库、版本、材料和待决动作。把问答和裁决记入候选的 `REVIEW.md`，同轮更新表格，回报该行去向。邮件沿用同一编号和版本。批准仅适用于讨论中的版本和动作，指代不清时先确认对应行。

每次候选入表、待审版本变化或会话恢复时，按目标仓库清点尚待用户审核的本地 PR 候选。同一仓库超过 5 项（即从第 6 项起），父 agent 自动派发[待审候选归并](references/exploration.md#待审候选归并)，与各仓库的下一轮探索并行。

## 已发起的 PR 总表

父 agent 默认在**开启对话的目录直属位置**维护 `PR_INDEX.md`。用户指定其他位置时记录其绝对路径，切换仓库或 worktree 后继续用同一文件。同一目录发起的各次 RepoScout 对话共用一张表。首次从[发布总表模板](assets/PR_INDEX.md)创建，已有文件保留。若启动目录在 Git 工作树内，将新建的本地总表加入该仓库本地排除规则。首次启用或恢复时，根据该工作区三表和审核材料里已有的发布记录补齐，经远端核实后入表。

每个实际在 GitHub 创建的 PR（含 Draft）占一行，以远端返回的完整 PR URL 去重。核实创建成功后，立即登记发起日期、目标仓库、候选编号、标题和可点击的 PR、Issue 链接，并在主对话回报。没有关联 Issue 时写“暂无”；多个 Issue 逐一列出。Issue 先发布时先将链接记在候选记录里，PR 创建后带入总表；后续新增关联则更新原行。查不到关联情况时标“待核实”。关闭或合并的 PR 保留原行。此表也可记录用户在 GitHub 手动发出并确认属于该工作区候选的 PR。

多个对话同时写同一总表时，共用按总表绝对路径确定的文件锁，持锁重读、按 PR URL 合并变更后原子替换。远端结果不明时先查证；用户询问“发起过哪些 PR”时，从这张总表列出链接。

## 派发和协调

1. 每个仓库设一个负责子 agent，派发仓库、起点、模式、目录和已获授权的范围。启动时按[探索与分配方法](references/exploration.md)同时检索领域前沿和上游近期 PR 的审核、合并及关闭情况。先用只读检索比较仓库，即使并发槽位不足也能排定首轮优先级。父 agent 以有价值的改动最终被上游合并为目标，在全局槽位、算力和用户优先级内动态调度。连续模式下，仓库负责人可用获分配的槽位创建方向子 agent，同时验证独立候选；资源不足时串行推进。
2. 子 agent 先读贡献说明，检查相关 Issue、PR、重复工作和署名政策。发现整仓政策冲突时立即报告并暂停该仓库的 PR 探索，其他仓库继续。若怀疑已有行为有误，先按[核实疑似缺陷](references/exploration.md#核实疑似缺陷)追溯原实现的依据，在支持的使用场景中检验预期与实测差异，再评估改动能否保留原有保证。新功能和优化则按各自的需求或基线验证。失败或重复的想法记录证据并关闭；有新反馈时更新优先级。
3. 子 agent 一发现缺条件就立即向父 agent 发消息，说明仓库/候选、用途、所需资源和可接受的替代方案；能并行的本地工作继续做。父 agent **每收到一项就立即向用户转达**，并说明已有授权能否满足、是否排队；需要补充时使用即时用户提问渠道。不要等待其他仓库汇总。用户已给的材料可直接分发。
4. 资源由父 agent 统一记账，它是本轮分配表的唯一写入者。先记录用户授权的主机、物理卡号或 UUID、目录、额度和期限，再按子任务记录等待、已分配和已释放。对机器别名核实是否指向同一台物理机。分配前和启动实验前均核实调度器预留、设备占用和实际作业归属。其他人的作业、同账号下非本轮的作业或归属不明的占用，一律记为占用并从可用池扣除；不得 kill、取消、抢占作业或重置设备来腾资源。发现冲突就退回分配、改用获准的空闲设备或排队，并告知负责 agent。同一物理设备、独占目录或已被整机独占的主机不得重复分配；共享主机上的不同卡可并行使用。给子 agent 明确主机、设备清单、运行目录和用途，让它显式绑定这些卡，核对进程实际可见的设备。只能对照本轮作业记录管理已确认归属的实验进程。
5. 例如同一台机器授权 GPU 0–15，A、B、C 分别需要 8、4、8 卡。若拓扑合适且卡空闲，可给 A 分 0–7、C 分 8–15，立即告知 B 排队；A 结束且确认作业退出后，再给 B 分 0–3。子 agent 完成实验、失败或中断均回报作业状态；父 agent 确认资源实际空闲再释放，并唤醒等待者。等待期间允许 B 继续 CPU 工作。恢复会话时先用运行记录核对实际作业，再重新分配。
6. 子 agent 只在获批范围内实验，记录基线/改动版本、配置、命令、结果和局限。实验未达到判据就如实记录，必要时修订假设。每个通过验证的候选按[审核与通知](references/review.md)交付改动和四份材料。父 agent 逐项检查、记录候选版本，立即通知用户可以审核。

## 主 agent 与用户答辩

每个候选进入待审时，由父 agent 本人在主对话中发起[逐项答辩](references/review.md#答辩)，附上候选版本和本地材料链接，陈述主张后让该项留在待审核，接受用户提问或裁决。子 agent 可以补查和补测，由父 agent 核对后亲自回应。仅需用户裁决时保持待审核，需要实际返工时转回处理中；用户明确批准该版本及发布动作后才提交。连续模式可并行探索其他候选。

## 停止、继续和发布

- **单个 PR**：第一份经验证的 PR 进入待审后，停止寻找新候选，处理该项审核意见。仅在用户明确批准对应版本和动作后提交或发布；按用户的关闭决定或批准的发布结果结束该仓库任务。
- **连续探索**：仓库负责人交接一份可审核的改动和材料后，立即在独立 worktree 开始下一项；没有现成候选时直接启动下一轮检索。父 agent 同轮将上一项移入待审核、把下一项登记为处理中，再对当前需要用户审核的版本发起答辩与通知。正在归并的一组候选交付整合结果后统一通知。启动下一项无需等待用户回复、邮件送达、发布或上游合并。一次实验失败、通知失败、已有 PR 等待审核或发布成功都不结束探索。收到用户停止指令后停止派新任务，协调运行中的作业收尾并保留结果；真正缺少必要输入时保留阻塞状态。运行依赖活跃会话，中断后从记录恢复。
- 审核意见可以直接交给原子 agent 修订。授权应能定位仓库、候选、版本和动作。PR、Issue 分别发布；批准 PR 不自动批准单独发 Issue。改动或拟发布正文有实质变化时，提交更新后的材料再审。父 agent 执行获批动作，记录远端链接并同步 PR 总表；网络结果不明时先核对远端，避免重复创建。
- 每次开 PR 前，父 agent 按[确认 PR 作者名单](references/review.md#确认-pr-作者名单)在主对话展示署名，请用户确认该版本的作者名单和发布动作，并在推送前核对实际提交。使用用户确认的人类 Git 身份作为新增提交的唯一作者，不加 AI 共同作者或相关 trailer，不改写他人的提交。审核时如实列出上游 AI 政策、披露及签署要求；若上游接受单作者并另要求在 PR 正文披露，则在待审正文中如实披露。若上游强制 AI 共同署名或禁止本次贡献形式，保留本地成果，说明具体冲突，不代用户签署不实声明或发布不符合要求的版本。
